# レシピ配信制限とアプリ内初回設定

## 変更

外部サイトの本文を取得するURL取り込みと、未確認の共有公開を停止した。旧画面からServer Actionを呼んでも外部へアクセスしない。手入力の登録はiOSと同じ家族内編集RPCを使い、栄養値の入力を必須にせず、値がない場合は未登録として扱う。

確認待ちの原稿は`recipe_content_holds`に登録する設計。原本、予定、購入済み記録、手入力の買い物品を削除しない。RLSはレシピ本体、材料、工程、栄養を制限する。編集とアレンジのSECURITY DEFINER関数も制限を確認する。配信対象がない静的料理をメニューへ復活させない。

保存済みの献立では元のIDとロックを保持し、「内容の確認中」と表示する。その料理を自動生成・変更候補には入れない。買い物リストには、その日の材料が含まれないことと主菜の選び直しを明示する。既にオフライン端末に取得済みの表示を即時消せるとは保証しない。iOSは今日・メニューの本文を永続保存しておらず、次回オンライン取得で反映される。

初回の人数・アレルギー・開始日の設定をアプリ内で完了できる。APIは家族の認証と利用期間を確認し、設定変更で無料期間を延長しない。Web版の同じRPCへ保存する。

## 独自原稿

`scripts/data/original-recipes-2026-11-07.json`に代替12品を別IDで用意した。材料・工程は独立に作成したAI原稿で、元サイトの文章を言い換える方法は使っていない。4人分、栄養未算出、実調理未確認。自動的に本番へ登録する処理には含めていない。実際の分量・加熱・時間の確認を残す。食肉の中心温度については[厚生労働省の加熱条件](https://www.mhlw.go.jp/content/11130500/000496685.pdf)を参照した。

旧シード・旧原稿の生成スクリプト3本は、確認待ちの本文を再投入しないよう停止した。適用済みの移行履歴は改変していない。既存の標準原稿の作成根拠・旧テンプレートの整理は別途確認が必要で、この修正だけで全コンテンツの権利確認完了とはしない。

## 適用順と残件

1. 本番へスキーマとRPCの移行を適用する。ここでは対象原稿のデータを変更しない。
2. APIと画面を本番へ反映し、認証・利用権限・読み込みを確認する。
3. 対象ごとの原稿ハッシュと未来の参照を再照合し、承認範囲の配信制限を適用する。個別家庭の原稿・識別子を公開リポジトリの変更記録には含めない。
4. ビルド14をTestFlightへ配布し、初回設定・献立・買い物・手入力の登録編集を実機確認する。
5. 内容の最終確認、審査用アカウントと連絡先、年額商品の審査画像、一般向け退会の有効化を済ませてからAppleへ提出する。一般受付は既存の指定どおり無効を維持する。

実装・ローカル検証と、本番適用・実機・Appleの審査結果を区別する。初版記録時点で本番DBへの適用確認が時間切れとなり、適用は未完了。
